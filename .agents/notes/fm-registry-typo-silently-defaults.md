## Notes

- Every mechanical caller of `bin/fm-project-mode.sh` must not discard its stderr warning (that warning is the only alarm for a malformed or unknown `data/projects.md` registry line - AGENTS.md section 2's registry format). As of this task the callers are: `bin/fm-fleet-sync.sh` (own line, now converted to a `<repo>: registry-invalid: ...` stdout line so it survives being invoked from a captured/backgrounded context), `bin/fm-spawn.sh` (own `2>/dev/null` removed, then narrowed so only a marked malformed-line warning reaches spawn's output), `bin/fm-home-seed.sh` and `bin/fm-remote-home-seed.sh` (already correct - no redirect). Re-grep `fm-project-mode\.sh` under `bin/` before trusting this list on a future change; a new caller must follow the same rule.
- The actionable session-start diagnostic for a malformed registry line has two independent sources, by design, not duplication: `bin/fm-bootstrap.sh`'s `fleet_sync_relay_filtered_output` relays a `FLEET_SYNC: <repo>: registry-invalid: ...` line only for a project that is actually cloned and synced that session; `bin/fm-bootstrap.sh`'s `project_registry_lint` (called from `detect_local_config`) is the comprehensive check - it runs `fm-project-mode.sh --lint`, which validates every line in `data/projects.md` in one process, and fires a `PROJECT_REGISTRY: <name>: ... - line: "..." - expected: ...` diagnostic regardless of clone state, so an uncloned or not-yet-synced project's malformed line is still caught. Both reuse `bin/fm-project-mode.sh` as the single owner of the registry format and of which lines are faults (one-owner rule) rather than re-parsing the format themselves.
- One rule governs every caller of `bin/fm-project-mode.sh`: report a malformed registry line, stay silent for every documented-normal state. The two normal states are `no registry at <path>` (AGENTS.md's "projects.md absent means rebuild it from the clones under `projects/`") and `project "<name>" not in registry` (a cloned project is legitimately unregistered until the captain registers it); reporting either turns the alarm into per-session noise nobody reads. A caller must not re-derive that split from warning wording: `bin/fm-project-mode.sh` marks exactly its malformed-line warnings `warn: registry-invalid: ...`, so the caller selects on the `registry-invalid:` marker and inherits the rule. Enforced today in `bin/fm-fleet-sync.sh`, `project_registry_lint` in `bin/fm-bootstrap.sh` (via `--lint`, which only ever emits malformed lines), and `bin/fm-spawn.sh`. Nothing mechanical stops a new caller from printing raw stderr instead, so the marker is a convention a reviewer has to check, not a guarantee.
- `bin/fm-project-mode.sh` is the single owner of "is this line well formed", so its warning coverage is where a gap in that answer gets fixed - not in a caller's filter. Its header carries the entry grammar field by field, and it validates a recognized entry line against that grammar end to end in one pass - every token between the name and the ` - ` separator must be accounted for, whether it sits before, inside, or after the brackets - rather than scanning one more position each time a new typo shape turns up. Recognition is an allowlist: a `- ` bullet without the separator, description, and line-final `(added <date>)` is prose, not a broken entry, and is never reported. If a malformed line is ever found unreported, the grammar in that header is what was incomplete - fix the grammar, do not add another positional scan. Its `--lint` mode validates every entry line in one process and prints `<name>\t<reason>\t<raw line>` per malformed entry; per-name lookups stop at the first line carrying that name, so only `--lint` reaches a malformed duplicate entry.
